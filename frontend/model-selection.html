Methodology

How "best" is scored

There's no single correct definition of "best" — it depends on what you're optimizing for. The composite score below is one reasonable default, built to reflect this project's actual constraint set (a federated-learning IDS for resource-constrained IoT/SDN nodes, where missing a rare attack is worse than a false positive, and inference happens continuously while training happens only periodically). Every number behind it is in the full table further down if you want to re-weight it yourself.

F1-macro (not accuracy) is the primary signal because it weighs every class equally — a model that nails "legitimate traffic" but misses "flood" scores no better than one that gets both half-right. The rarest-class F1 is broken out separately and weighted extra because in an IDS, the rarest attack class ( on MQTTset, on DataSense) is disproportionately the one you can't afford to miss.

Inference latency
65%
Train time
35%

Inference is weighted higher than train time because it runs continuously in production (every packet/window), while training happens on a periodic schedule. Model size is reported per-model in the full table but isn't scored numerically — "200 trees," "25,064 parameters," and "15,227 support vectors" aren't comparable units, so it's left as a qualitative read rather than forced into a number.

Read before you commit

What this score doesn't capture

Subsample caps affect some models' reported cost. Kernel SVMs, Gaussian Process, Label Spreading, and a few ensembles were trained on a fixed-seed subsample (see the "cap" note in the full table) because the full set was impractical. Their quality scores are still measured against the full test set, but their train-time numbers would very likely be worse on the full training set — treat their cost score as a floor, not a ceiling.
These weights are a starting point, not a law. If your deployment genuinely doesn't care about inference latency (e.g. batch/offline analysis rather than live traffic), re-run this with cost weighted near zero — several interpretable and boosting models would swap places. The raw numbers to do that yourself are in the full table.
Composite score is not statistical significance. A 0.3-point gap between two boosting variants on one dataset is well within run-to-run noise from random seeds, hardware, and library versions — treat models within a couple of points of each other as tied, not strictly ordered.
Interpretability isn't in the score at all. If your project needs to explain why a packet was flagged (audit trail, compliance, thesis defense questions), that's a hard requirement no composite score should override — see the "most interpretable" scenario card above.
