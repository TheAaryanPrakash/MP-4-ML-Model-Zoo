50 Models, One Split: An ML Model Zoo for IoT/IIoT Intrusion Detection

From everyday production staples to rare, rarely-packaged techniques pulled off GitHub/PyPI -- one identical preprocessing pipeline and train/test split per dataset, run through ~50 classic ML classifiers each, to find out which model family actually earns its keep for network intrusion detection. Companion to MP-2-ML-vs-DL and MP-3-DataSense-ML-vs-DL, which each ran an 11-model ML-vs-DL comparison on these same two datasets.

Trying to pick one model for an actual deployment? See the Model Selection Report -- a multi-criteria composite score, scenario-based picks, and the full breakdown of how "best" was defined.

Deep Dive: Feature Selection, Malicious/Benign Detection & Scaling to 40 Lakh Rows

Three questions the leaderboard alone doesn't answer: which features each model family actually leans on, how well the zoo separates malicious traffic from benign specifically (not just the 6-8-way attack-type split), and what would have to change to run this pipeline on a dataset roughly 12-90x larger than what's here today. Everything below is computed from the same fixed-seed train/test split every other tab uses.

Feature selection by model family

One representative model per major family, retrained on the identical split, scored two ways: each model's own native importance (impurity-based for trees, |coefficient| for linear, per-feature shape function for the glass-box EBM) and model-agnostic permutation importance (how much F1-macro drops when a feature is shuffled) on a held-out test subsample -- so families that expose no native importance at all (KNN) are still directly comparable to the ones that do.

Identifying malicious vs. benign traffic

Every model in the zoo is trained multiclass (attack-type, not just attack/benign), but every multiclass confusion matrix already contains the binary answer: collapse every non-benign class into "malicious" and every model's existing predictions -- no retraining -- yield a benign-vs-malicious verdict. The two numbers that matter operationally for an IDS are false-negative rate (a real attack waved through as benign) and false-positive rate (legitimate traffic wrongly blocked).

Where the two disagree, non-linear structure is doing the work.

Scaling to ~40 lakh (4,000,000) row datasets

MQTTset here is 330,936 rows across 33 features; DataSense is 45,055 rows across 109 features -- a real deployment target of ~40 lakh rows is roughly 12x and 89x larger, respectively. The zoo's own harness already had to answer "what breaks first at scale" to train 50 models on today's data; the table below shows what it found, extrapolated to the current dataset's actual numbers.

Complexity classExample familiesBehavior at current scaleWhat happens at ~40 lakh rows
Feature selection first. The importances above aren't just descriptive -- they're a scaling lever. Dropping near-zero-importance features (DataSense's long tail of per-device one-hot columns is the obvious target) shrinks memory and training cost linearly, and disproportionately helps every distance- or kernel-based method whose cost grows with dimensionality.
Favor near-linear-time families. Histogram-based gradient boosting (XGBoost/hist, LightGBM, HistGBM) and bagged trees scale roughly log-linearly and were already the fastest strong performers at today's scale. Kernel SVM, Gaussian Process, and graph-based Label Spreading are O(n^2)-O(n^3) and needed hard subsample caps (12k / 3k / 5k rows respectively) even at 45k-330k rows -- at 4M rows they're not viable at all without a fundamentally different (approximate) formulation.
Sample selectively, not blindly. RUSBoost's naive random undersampling produced the worst malicious-detection F1 of any model on both datasets, while LightGBM's GOSS -- which keeps the highest-gradient (hardest) examples and subsamples the rest -- stayed competitive with full-data boosting. At 4M rows, principled sampling (gradient-based, or stratified to preserve rare attack-class ratios) should replace naive random subsampling, not just reduce row count.
Inference cost matters as much as training cost. KNN "trains" in near-zero time because it's lazy, but its inference cost scales with the stored training-set size -- already ~15-80x slower per sample than XGBoost/HistGBM at today's scale. For a live inline IDS, that gap only widens as training data grows toward 4M rows; boosting/tree families keep sub-millisecond inference almost independent of n.
Don't centralize what doesn't need centralizing. The survey paper's target architecture is federated learning, which is also the natural answer to the memory ceiling: train locally per device/site (DataSense is already organized per-device) and aggregate (FedAvg-style) rather than materializing 4M rows as one in-memory array on one machine. Where centralized training is still needed, mini-batch/partial_fit-capable learners, Parquet/columnar storage over CSV, and float32 over float64 keep a single training pass from ever needing the whole dataset resident at once.

Methodology

Same split, every model. Every model on a given dataset sees the identical preprocessed train/test split (reused verbatim from the sibling MP-2/MP-3 repos' preprocess.py), so differences in the leaderboard reflect the model, not the data.
Subsampling for models that don't scale. Kernel SVMs, Gaussian Processes, graph-based Label Spreading, and a few ensemble methods that internally resample per base estimator (Bagging-KNN, the imbalanced-learn ensemble family, Stacking) are capped to a fixed-seed random subsample of the training set when the full set would make training impractical -- the same approach the sibling projects used for kernel SVM. The exact cap used, if any, is recorded per model in the Full Table and Model Guide.
Model coloring. With ~50 models, a one-hue-per-model scheme is impossible under a colorblind-safe categorical palette (the practical ceiling is about 8 distinguishable hues). Every model's ~13 raw families instead fold into 8 broader color groups; every chart also direct-labels or tooltips the exact model name so color is never the only way to identify a point.
Two techniques implemented from scratch. The Extreme Learning Machine and the Self-Organizing-Map classifier aren't well-packaged on PyPI for scikit-learn-style multiclass classification, so both are small from-scratch implementations (see scripts/custom_models.py) rather than a maintained library. Neither is deep learning: the ELM's hidden layer is fixed random weights with a closed-form ridge-regression readout (no backpropagation), and the SOM classifier is a competitive-learning lookup table, not a differentiable network.
Not every package survived. Deep Forest / gcForest (the DF21 package) has no compatible wheel for this environment and was dropped before training started. Standalone RuleFit doesn't support multiclass classification at all (neither the standalone package nor imodels' version) and was likewise dropped from the registry. Any model that failed during training is reported in the Failed Runs tab rather than silently omitted.
